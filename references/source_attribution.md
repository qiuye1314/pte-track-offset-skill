# 接手源码第一件事：判定它属于哪个游戏 / 哪个版本

> 教训来源：2026-10-26。用户给的源码其实是**和平精英（国服）**，
> 没先判断就按旧结论往下改，导致偏移、追踪函数、写回组全部对不上，
> 白试了十几轮。**判定成本 5 分钟，判错的成本是几小时。**

---

## 零、铁律

**任何源码到手，先回答三个问题，再动一行代码：**

1. 它面向哪个**游戏 + 区服**？（和平精英 / 国际服 / 台服 / 韩服 / 越南服）
2. 它面向哪个**版本号**？（1.38 / 4.5 / 4.6 / 4.7 …）
3. 它的**追踪实现是哪种形态**？（fmov 返回值桩 / 双 float3 参数函数 / 读全局坐标对象）

**三个问题没答案，就不要套用任何现成偏移。**

---

## 一、包名判定（最快，一眼定区服）

| 包名 | 游戏 / 区服 |
|---|---|
| `com.tencent.tmgp.pubgmhd` | **和平精英（国服）** |
| `com.tencent.ig` | **PUBG MOBILE 国际服** |
| `com.rekoo.pubgm` | 台服（PubgMobile TW） |
| `com.pubg.krmobile` | 韩服（Korea） |
| `com.vng.pubgmobile` | 越南服 |
| `com.tencent.igce` | 国际服 IGCE 包（常见于 4.7.3） |

**命令：**

```bash
grep -rn "com\.tencent\.\|com\.rekoo\.\|com\.pubg\.\|com\.vng\." src/ include/ | head
```

**注意**：很多工程里包名写了不止一处（找进程、启动游戏、初始化绘制）。
**必须全部替换**，漏一处就会出现"绘制正常但追踪不生效"这类怪现象。

---

## 二、偏移指纹判定（没写包名时用）

拿 `UWorld` 的锚点值反查版本，这是最稳的指纹：

| UWorld 锚点 | 自身链 | 判定 |
|---|---|---|
| `0x1771CC38` | `+0xc0 +0x88 +0x30 +0x3540` | 和平精英（较新版本） |
| `0x15772758` | — | 和平精英（旧版本，已废弃） |
| `0xF621D90` | `+0x38 +0x78 +0x30 +0x28D8` | **PUBG 4.6 国际服** |
| `0xF1D5F70` | 矩阵 `+0xC0 +0x590` | PUBG 4.5 国际服 |

矩阵锚点也能交叉验证：

| 矩阵锚点 | 判定 |
|---|---|
| `0x176E6EE0` → `+0x20 +0x270` | 和平精英 |
| `0xF5F4370` → `+0x20 +0x270` | PUBG 4.6 国际服 |

## 三、追踪实现形态判定（决定写回方式）

| 形态 | 判据 | 写回组 |
|---|---|---|
| **fmov 返回值桩** | `fmov s2,s5 / s1,s4 / s0,s3 / ret`（字节 `a240201e8140201e6040201ec0035fd6`） | `s3/s4/s5` |
| **双 float3 参数函数** | 入口 `stp s0,s1 / stur s2` + `stp s3,s4 / stur s5`，无直接 `BL` 调用者 | **要实测**，4.6 国际服是 `s0/s1/s2` |
| **读全局坐标对象** | 从固定全局地址读坐标结构（IGCE 4.7.3 那种） | 不写寄存器，改写全局 |

**扫描命令（确认 fmov 桩在不在）：**

```bash
python3 - <<'PY'
d=open('libUE4.so','rb').read()
pat=bytes.fromhex('a240201e8140201e6040201ec0035fd6')
i=d.find(pat)
print('fmov桩:', '存在 @0x%X'%(i) if i>=0 else '不存在')
PY
```

**4.6 国际服实测：不存在。别再浪费时间扫。**

## 四、版本串判定（有注释/字符串时最准）

UE 的 `ensure()` 会把 `__FILE__` 打进 so，里面带发布号：

```
D:\Release4.6.0\AS\Survive\Source\ShadowTrackerExtra\Weapons\STEShootWeaponProjectComponent.cpp
                ^^^^^ 就是版本
```

找法：搜 `D:\\Release` 或 `Survive\\Source`。

```bash
strings -a libUE4.so | grep -m3 "Release[0-9]."
```

## 五、拿"能跑的旧工程"当参照时

用户给一份「已经在别的游戏上跑通的工程」时，**不要直接移植它的偏移**，先对照：

| 要对比的 | 为什么 |
|---|---|
| 包名 | 定区服 |
| UWorld 锚点 + 自身链 | 定版本 |
| 矩阵锚点 | 交叉验证 |
| 追踪函数偏移 + 形态 | 决定写回组 |
| 骨骼链（Mesh / Array / Count） | 决定能不能读到骨骼 |
| 写回组 | **最容易错的一环** |

**跑通 ≠ 通用。** 同一款游戏换个区服，上面六项至少四项不一样。

## 六、判定脚本

```bash
python3 scripts/detect_source_target.py <工程目录>
```

输出：包名候选、偏移指纹命中、疑似版本、追踪形态、建议的写回组。

## 七、这次踩的具体坑（复盘）

| 阶段 | 我错的 | 正确做法 |
|---|---|---|
| 拿到源码 | 直接按「旧结论 = 国服 1.38」往下改 | 先 `grep com.tencent` 看包名 |
| 移植偏移 | 沿用国服 UWorld `0x1771CC38` | 先判定，4.6 应换 `0xF621D90` |
| 找追踪函数 | 拿 `0xA0FB548` 往国际服套 | 先判形态，国际服没有 fmov 桩 |
| 写回 | 沿用 `s3/s4/s5` | 先实测，4.6 要 `s0/s1/s2` |
| 失败后 | 反复调参数 | **先怀疑判定错**，回去重新认游戏 |

**核心教训：参数调不通时，先回头确认"游戏/版本判对了吗"，不要继续调参数。**
